# Самостійна робота №20

**Виконала: Успенська Емілія**

**Тема:** Реалізація exponential backoff.

## Опис роботи

у програмі реалізувала клас RetryPolicy для повторного виконання операцій після помилок. використала експоненційну затримку (exponential backoff), яка збільшується після кожної невдалої спроби, та jitter для випадкової зміни часу очікування. метод Execute<T> дозволяє виконувати різні операції, а делегат shouldRetry визначає, чи потрібно повторювати спробу після помилки для перевірки створила три сценарії: успішне виконання після двох помилок, постійна невдача після вичерпання спроб та заборона повторення для певного типу винятку

## Висновок

у цій самостійній роботі я реалізувала клас RetryPolicy та jitter, перевірила успішне й невдале виконання операцій та використання делегата shouldRetry. з'ясувала, що патерн Retry з exponential backoff краще застосовувати для тимчасових збоїв мережі або сервера, але він не підходить для постійних помилок і операцій, повторне виконання яких може спричинити небажані наслідки

## Контрольні запитання

**1. Чому експоненційна затримка зазвичай ефективніша за фіксовану для тимчасових збоїв?**

тому що час очікування поступово збільшується, що зменшує навантаження на сервер і дає йому більше часу для відновлення

**2. Для чого потрібен jitter і як він зменшує ризик одночасних повторних спроб?**

jitter додає випадкову зміну до часу затримки, щоб різні клієнти не повторювали запити одночасно та не перевантажували сервер

**3. Яку роль відіграє делегат shouldRetry у власній реалізації політики повторних спроб?**

делегат shouldRetry перевіряє виняток і визначає, чи потрібно повторювати операцію, чи одразу припинити виконання

**4. У яких випадках повторна спроба не є безпечною та її слід заборонити?**

коли повторне виконання може призвести до дублювання операції, наприклад повторного списання коштів або створення однакових записів. також не варто повторювати операції з некоректними даними
